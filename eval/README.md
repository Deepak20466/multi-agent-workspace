# Evaluation pipeline

Generates testsets from the sample corpus, runs the RAG/SQL/doc agents
against them, and scores the results. See `main.py`'s `Evaluation`
section in the top-level README for the full CLI reference; this file
covers dataset provenance and how to reproduce a baseline locally.

## Local (Ollama) vs. cloud

Every LLM call in this pipeline (RAG generation, RAGAS's internal judge +
embeddings, doc-eval judging, testset ground-truth generation) resolves
through `src.llm_factory.build_llm`, which reads `agents.llm_backend` /
`agents.ollama_model` / `agents.ollama_base_url` from `config.yaml` --
the same backend every agent uses. With the shipped `config.yaml`
(`llm_backend: ollama`), the whole pipeline runs fully offline against a
local Ollama server; no `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` is required.
Set `agents.llm_backend: anthropic` (or `LLM_BACKEND=anthropic`) to use
Claude instead.

RAGAS's `evaluate()` defaults to an OpenAI-backed judge/embeddings model
when none are passed explicitly -- `run_rag_eval` always passes the
project's own configured backend (`_ragas_judge_llm_and_embeddings` in
`run_ragas_eval.py`) plus a local `sentence-transformers/all-MiniLM-L6-v2`
embedding model (the same one `VectorStore` uses), so this never
silently falls back to requiring an OpenAI key.

## Dataset provenance

`eval/testset.json` (RAG), `eval/sql_testset.json`, and
`eval/doc_testset.json` are not checked in as static fixtures -- they're
generated by `generate_testset.py` from:

- **RAG/doc testsets**: `data/sample_documents/` (`refund_policy.txt`,
  `sales_summary.txt`) -- the project's existing sample corpus.
  `ground_truth`/`expected_contains` are generated by the configured LLM
  from each document's actual chunked content.
- **SQL testset**: the live schema of whatever `DATABASE_URL` points at
  (seed with `python eval/seed_sql_db.py` first if empty).

Regenerate at any time:

```bash
python eval/seed_sql_db.py                                            # idempotent
python eval/generate_testset.py --type all --sample-dir data/sample_documents --output-dir eval
```

## Running a baseline

```bash
python eval/run_ragas_eval.py --type all --output eval/results_v3.json
python eval/check_gates.py --results eval/results_v3.json             # optional: CI quality gate
```

`results_v3.json` is the results file `check_gates.py` and CI
(`.github/workflows/ragas_eval.yml`) both read by default. Each section
(`rag`/`sql`/`doc`/`retrieval`/`sql_guardrail`) degrades to
`{"status": "skipped: <reason>"}` instead of raising when its
prerequisites aren't met, so a partial local setup still produces a
usable results file.

## Baseline (2026-08-09, `qwen2.5:0.5b`)

```
PASS: rag.faithfulness=0.750      (gate=0.750)
FAIL: rag.answer_relevancy=0.230  (gate=0.700)
PASS: rag.context_precision=1.000 (gate=0.700)
PASS: rag.context_recall=1.000    (gate=0.600)
FAIL: sql.accuracy=0.429          (gate=0.800)
PASS: doc.accuracy=1.000          (gate=0.800)
retrieval: skipped (testset carries no relevant_chunk_ids)
sql_guardrail.pass_rate=1.000 (9/9, no LLM involved)
```

Real, unmocked run against the locally configured `qwen2.5:0.5b` (see
`eval/results_v3.json`) -- gate failures reflect genuine model quality,
not a broken pipeline:

- **`rag.answer_relevancy` low**: this metric reverse-engineers questions
  from the RAG answer and measures their similarity to the original
  question -- a 0.5B model's short/generic answers give it little to
  work with. `faithfulness`/`context_precision`/`context_recall` (whether
  the answer sticks to retrieved context) all pass comfortably.
- **`sql.accuracy` low**: `generate_testset.py`'s SQL testset generation
  also uses the configured local LLM, and `qwen2.5:0.5b` (1) wrote all 7
  questions in Chinese rather than English, and (2) used
  `EXTRACT(YEAR FROM ...)`/`MONTH(...)`-style functions in 3 of 7
  ground-truth/generated queries -- valid Postgres, not valid SQLite
  (the eval DB here). Those 3 fail with a real `sqlite3.OperationalError`
  (see `eval/results_v3.json`'s `sql.details`); the other 4
  (aggregate/group-by queries) scored correctly.

Re-run with a larger `agents.ollama_model` (or `agents.llm_backend:
anthropic`) for a stronger baseline -- the pipeline itself is
model-agnostic, and gates existing to catch exactly this kind of
model-quality regression is the intended behavior, not a bug.
